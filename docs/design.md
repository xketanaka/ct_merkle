# ct_merkle 設計メモ

RFC 6962 / RFC 9162 §2.1 に準拠したマークルツリーの Ruby 実装について、設計上の判断とその理由を記録する。

各クラス・メソッドの仕様は [reference.md](reference.md) を参照。この文書は「なぜそうしたか」を残すためのもので、仕様の正はリファレンスとする。

## 1. 基本方針

- **追記型を基本にする**: ツリーは追記のみ。バッチ型の用途も「追記されていないツリー」として同じクラスで扱う。追記型はバッチ型を包含しており、2 つのクラスに分ける理由がない。
- **生成と検証を分離する**: 証明を検証する側（CT のクライアントなど）はツリー全体を持たない。検証は `Tree` なしでできるようにする（`Verifier`、証明オブジェクトの `verify`）。
- **基準のツリーは `tree_size:` で指定する**: 証明やルートは「どのサイズの時点のツリーに対するものか」とセットで意味を持つ。基準のツリーはキーワード引数 `tree_size:` で指定し、省略した場合は現在のサイズを使う。
- **ハッシュ値はバイナリで持ち、公開 API では `CTMerkle::Digest` で返す**。
- **依存は標準ライブラリだけにする**: 実行時に使うのは `digest` のみ。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 葉（リーフ） | ツリーに追加した 1 件のデータ |
| `index` / `leaf_index` | 追加した順番での葉の位置。0 から数える。一度決まったら変わらない |
| `tree_size` | 葉の数（= 追加した件数）。有効なインデックスは `0`〜`tree_size - 1` |
| リーフハッシュ | `HASH(0x00 ‖ data)` |
| ノードハッシュ | `HASH(0x01 ‖ left ‖ right)` |
| ルートハッシュ (MTH) | ツリー全体のハッシュ。空のツリーのルートは `HASH("")` |
| 包含証明 (Inclusion Proof) | ある葉が、サイズ `tree_size` のツリーに含まれていることの証明 |
| 整合性証明 (Consistency Proof) | サイズ `old_size` のツリーの葉の並びが、サイズ `new_size` のツリーの先頭にそのまま入っていることの証明 |
| 満タンの部分木 | 葉の数が 2 のべき乗で、位置もそろった部分木。追記しても二度と変わらない |

## 3. API の設計判断

### 3.1 証明を作るメソッドの引数

`inclusion_proof(index, tree_size:)` と `consistency_proof(old_size, tree_size:)` は、どちらも「第 1 引数が証明の対象、`tree_size:` が基準となるツリー」という同じ形にした。

整合性証明の 2 つのサイズは同列に見えるが、新しいサイズは包含証明の `tree_size` と同じく「基準のツリーの指定」と考えられる。検討した案と、採用しなかった理由は次のとおり。

| 案 | 書き方 | 採用しなかった理由 |
|---|---|---|
| 位置引数 2 つ | `consistency_proof(3, 5)` | どちらが古いサイズか覚えておく必要がある |
| 両方キーワード | `consistency_proof(old_size: 3, new_size: 5)` | 必須のキーワード引数が冗長 |
| Range | `consistency_proof(3..5)` | `3...5` の扱いなど、Range の意味とずれる |

できあがった証明では 2 つのサイズが同列に並ぶので、属性名は `old_size` / `new_size` とした。

### 3.2 `Tree#at` と `Snapshot`

`tree_size:` 引数の代わりに、「どの時点のツリーか」をオブジェクトとして表せるようにした。ツリーは追記しかできないので、`Snapshot` は元のツリーを参照するだけで、コピーを持つ必要がない。

### 3.3 `index_of` / `inclusion_proof_by_hash`

証明を受け取る側はインデックスを知らないことがある（RFC 6962 の SCT にはインデックスが含まれず、CT のクライアントは `get-proof-by-hash` を使う）。そのため、リーフハッシュから葉を探す API を v1 に含めた。

- 同じハッシュが複数ある場合は最初のインデックスを返す（CT の実装と同じ）
- 見つからない場合は例外ではなく `nil` を返す（Ruby の `find` などと同じ考え方）
- 実装のために「リーフハッシュ → インデックス」の対応表を持つので、葉の数に比例してメモリを使う

### 3.4 証明オブジェクトの属性名

属性名は RFC 9162 §4.12 / §4.13 の `InclusionProofDataV2` / `ConsistencyProofDataV2` に合わせた（`inclusion_path`、`consistency_path` など）。RFC 6962 の `audit_path` ではなく RFC 9162 の名前にしたのは、RFC 9162 の定義では証明がインデックスとサイズも含んでおり、このライブラリの証明オブジェクトと範囲が一致するため。

証明オブジェクトは `Data` で実装し、frozen な値オブジェクトとした。

### 3.5 検証の戻り値と例外

- `verify` は `true` / `false`、`verify!` は失敗時に例外を投げる、の 2 本立てにした
- 失敗の原因を `MalformedProofError`（証明の形が不正）と `RootMismatchError`（ルートが一致しない）に分けた。前者は実装のバグや入力の取り違え、後者は改ざんやログの不正を示すことが多く、デバッグのときに区別できると便利なため
- 引数の型が違うなど、呼び出し方そのものが誤っている場合は `ArgumentError` とする。`verify` でも `false` にはしない

## 4. ハッシュ値の扱い

### 4.1 内部はバイナリ、公開 API は `Digest`

ハッシュ計算の入力はバイト列なので、内部では BINARY エンコーディングの String に統一した。hex で持つと、ノードを計算するたびに変換が必要になり、メモリも 2 倍になる。

公開 API でただの String を返すと、hex との変換に毎回 `pack` / `unpack1` を書く必要があり、バイナリと hex の取り違えも起きやすい。そこで、バイト列を包む薄い値オブジェクト `CTMerkle::Digest` を返すことにした。

- クラス名に `CTMerkle::Hash` は使わない。モジュール内で組み込みの `::Hash` を隠してしまうため
- `Hasher` はツリーの計算で大量に呼ばれるので、`Digest` で包まずバイナリの String を使う

### 4.2 引数として受け付ける値

ハッシュ値の引数は `Digest` と、生のバイト列の String だけを受け付ける。String を hex や base64 として自動で解釈することはしない。自動で判別すると、取り違えたときに気づけなくなるため。

### 4.3 比較

- `Digest#==` は、相手が `Digest` でも String でもバイト列だけで比較する。String のエンコーディングは見ない（UTF-8 のエンコーディングがついたまま読み込まれた値でも比較できるようにするため）
- `eql?` / `hash` は `Digest` 同士でだけ等しいとする。`String#hash` とそろえることはできないので、Hash のキーとしての一貫性を優先した
- `to_str` は定義しない。定義すると暗黙に String として扱われ、バイナリと hex を取り違えやすくなる。そのかわり `str == digest` は常に `false` になるので、比較するときは `Digest` を左辺に置く

### 4.4 `to_s` と `inspect`

どちらも hex にした。`to_s` は標準ライブラリの `Digest::Base#to_s` が hex を返すのに合わせた。

## 5. 直列化

### 5.1 方針

外部の形式（RFC 6962 の JSON API、Rekor、RFC 9162 のバイナリ形式）は、キー名、ハッシュの表現、含まれる項目がそれぞれ違う。gem がそれぞれを直接サポートすると、各仕様の変更に追従し続ける必要がある。そこで、gem は自分の形式（`to_h` / `from_h`）だけを定義し、外部の形式との変換は利用者に任せることにした。`new` と `Digest.from_hex` / `from_base64` があれば、変換は数行で書ける。

### 5.2 形式の位置づけ

ct_merkle 独自の形式で、特定の標準には準拠しない。中身は RFC 9162 の `InclusionProofDataV2` / `ConsistencyProofDataV2` から `log_id`（CT 固有のログ識別子）を除き、JSON にできる Hash にしたもの。

| このgemのキー | RFC 9162 のフィールド |
|---|---|
| `leaf_index` | `InclusionProofDataV2.leaf_index` |
| `tree_size` | `InclusionProofDataV2.tree_size` |
| `inclusion_path` | `InclusionProofDataV2.inclusion_path` |
| `old_size` | `ConsistencyProofDataV2.tree_size_1` |
| `new_size` | `ConsistencyProofDataV2.tree_size_2` |
| `consistency_path` | `ConsistencyProofDataV2.consistency_path` |
| （なし） | `log_id` |

証明を JSON で表すための広く使われている標準はない。RFC 6962 の JSON は `tree_size` を含まず証明だけで完結しない。RFC 9162 の JSON は中身がバイナリで、実際にもほとんど使われていない。

### 5.3 ハッシュの表現

`encoding:` の既定は `:hex`。`Digest#to_s` や `inspect` と表現をそろえ、人が読んだり比べたりしやすくするため。CT（base64）に合わせても、キー名が違うので結局は変換が必要になり、利点が小さい。`encoding: nil`（`Digest` のまま返す）は、証明オブジェクトの属性から取り出せるので用意しない。

### 5.4 互換性

この形式の互換性は、gem のバージョン（セマンティックバージョニング）で保証する。キー名、キーの追加・削除、ハッシュ値の表現、`encoding:` の既定値を変えるのはメジャーバージョンを上げるときだけとする。`from_h` は未知のキーを `ArgumentError` にするので、キーの追加も破壊的変更になる。

### 5.5 v1 で提供しないもの

- `to_json`：既定のエンコーディングを決める必要があり、ActiveSupport などが定義する `to_json` とも競合しやすい
- RFC 9162 のバイナリ形式：CT 固有の `log_id` を含み、マークルツリーの範囲を超える。RFC 9162 の API を提供している運用中のログもほとんどない

## 6. 実装の方針

- **ツリーの保持**：満タンの部分木のハッシュを、追記のたびにすべて保存する。満タンの部分木は追記しても変わらないので、過去のどのサイズのルートや証明も、保存済みのハッシュを組み合わせて O(log n) で計算できる。メモリは葉の数に比例する（葉 100 万件でおよそ 290MB）
- **証明の生成**：RFC 9162 §2.1.3.1 / §2.1.4.1 の再帰的な定義（`PATH` / `SUBPROOF`）をそのまま実装した
- **証明の検証**：RFC 9162 §2.1.3.2 / §2.1.4.2 の手順をそのまま実装した。ただし、ハッシュの長さの確認、`old_size == 0`、`old_size == new_size` などは、手順の前に明示的に確認する
- **スレッドセーフではない**：複数のスレッドから追記する場合は、利用する側で排他制御する

## 7. テストの方針

- transparency-dev/merkle（Go）の既知の値と、テストベクタ（JSON 196 件）で確認する
- RFC の定義をそのまま書いた素朴な実装と、サイズ 1〜40 のすべての root と証明を照合する
- Go の実装とは 1 件だけ結果が異なる。`old_size == new_size` でルートの長さが正しくない場合、Go は長さを確認せず成功とするが、ct_merkle は長さの違うハッシュを常に不正とする方針を優先した（`test/vectors_test.rb` の `DEVIATIONS`）
